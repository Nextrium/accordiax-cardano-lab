# Accordiax Cardano Integration Architecture

## 1. Purpose

This document defines the engineering architecture for integrating Cardano settlement infrastructure into Accordiax.

Accordiax is an existing agreement-and-escrow platform. The existing application handles the user-facing trust workflow:

- request;
- structured offer;
- agreement;
- payment/escrow;
- delivery;
- approval;
- release or dispute.

The Cardano integration changes the settlement layer underneath that workflow. The goal is to move from a custody-dependent escrow mechanism toward non-custodial, verifiable on-chain settlement while keeping the Accordiax application responsible for agreement context, user experience, workflow state and dispute processes.

This document describes the target architecture independently of the Catalyst proposal questions.

## 2. Architectural principles

### 2.1 Agreement first

The agreement is the primary business object.

Cardano should enforce the settlement conditions derived from the agreement rather than becoming the application's entire state model.

### 2.2 Non-custodial settlement

Accordiax should not need to take custody of the protected settlement asset in order to coordinate a transaction.

The production direction is for the settlement contract and the participating wallets to control the on-chain asset flow.

### 2.3 Asset agnostic

The escrow mechanism should not depend permanently on NXTEST.

NXTEST is a controlled development asset used to validate the mechanics.

Production settlement should support verified Cardano settlement assets, including selected stablecoins, subject to issuer, policy and regulatory validation.

### 2.4 Blockchain abstraction for ordinary users

Users should not need to understand:

- UTxOs;
- collateral;
- minimum ADA;
- transaction construction;
- validator scripts;
- redeemers; or
- native-asset accounting.

The application should abstract these details while preserving user-controlled wallet authorization where required.

### 2.5 External-user activity

Production architecture must make it possible for genuine users to generate their own qualifying Cardano activity.

Operational transactions should not be artificially generated by Accordiax's own declared wallets for the purpose of producing adoption metrics.

### 2.6 Evidence-driven engineering

Confirmed behaviors, unresolved problems, and architectural assumptions are tracked separately.

Preprod success is not treated as production readiness.

## 3. Logical architecture

```text
                         ACCORDIAX APPLICATION
                                  |
                   +--------------+--------------+
                   |                             |
             Agreement Layer               User Identity
                   |                             |
                   |                     CIP-0170 Layer
                   |                             |
                   +--------------+--------------+
                                  |
                           Settlement Orchestrator
                                  |
                    +-------------+-------------+
                    |                           |
              Asset/Policy Layer          Wallet Layer
                    |                           |
          Verified stablecoins          User authorization
                    |                           |
                    +-------------+-------------+
                                  |
                           Cardano Escrow
                           Plutus V3 / eUTxO
                                  |
                         Cardano blockchain
                                  |
                         Dune / public metrics
```

The architecture deliberately separates the application layer from the settlement layer.

## 4. Application layer

The Accordiax application remains responsible for:

- user accounts;
- agreement creation;
- structured offers;
- agreement acceptance;
- scope, price, timeline and deliverables;
- delivery state;
- user-facing approval;
- dispute initiation;
- administrative dispute workflow;
- transaction history;
- user notifications;
- marketplace/commerce workflows.

The application does not replace on-chain settlement with database state.

Instead, the application records the business context that maps to the on-chain settlement transaction.

## 5. Agreement-to-settlement mapping

Each protected agreement should have a deterministic settlement representation.

Conceptually:

```text
Accordiax Agreement
    |
    +-- agreement identifier
    +-- buyer / initiator
    +-- seller / provider
    +-- settlement asset
    +-- quantity
    +-- delivery condition
    +-- approval condition
    +-- dispute state
    |
    v
Escrow transaction
    |
    +-- escrow datum
    +-- protected asset
    +-- release/refund conditions
```

The exact final datum schema remains a production-design task.

The current prototype demonstrates the validator and transaction mechanics but should not be assumed to be the final business datum structure.

## 6. Cardano escrow layer

The current laboratory validates a Plutus V3 spending validator.

Current validated characteristics include:

- Plutus V3 script;
- escrow funding;
- native-asset custody at the script address;
- inline datum;
- Release redeemer;
- beneficiary output;
- exact asset conservation;
- ADA conservation;
- transaction fee calculation;
- on-chain confirmation.

The production contract must additionally address:

- refund states;
- dispute-related state transitions where appropriate;
- final beneficiary representation;
- supported asset/policy validation;
- security review;
- failure modes;
- upgrade strategy;
- mainnet operational constraints.

## 7. Settlement asset layer

### Current prototype

The controlled development asset is NXTEST.

It proves that the escrow mechanism can hold and release a native Cardano asset.

### Production direction

The protocol should remain asset-agnostic.

A supported production asset should be validated through its policy/issuer characteristics before it is accepted by Accordiax.

The current proposal direction emphasizes existing verified stablecoins rather than launching an Accordiax-native stablecoin as part of the pilot.

The exact production stablecoin(s), issuer relationship and regulatory structure are not yet finalized.

## 8. Identity layer

CIP-0170 is a proposed supporting integration.

Its intended role is to improve the relationship between:

- an Accordiax participant;
- their Cardano credentials;
- organization/user identity;
- attestations and reputation where appropriate.

Identity should remain a supporting trust layer rather than becoming the sole authorization mechanism for escrow.

The user experience should allow Accordiax to associate the application-level participant with the appropriate Cardano credentials while preserving appropriate privacy boundaries.

The exact CIP-0170 attestation flow remains a production integration task.

## 9. Wallet and transaction abstraction

The transaction-builder layer is responsible for converting the business action into a Cardano transaction.

The production system must handle:

- UTxO selection;
- transaction construction;
- minimum ADA requirements;
- fees;
- collateral;
- change;
- signing;
- submission;
- confirmation;
- error reporting.

Users should not need to manually calculate these values.

The laboratory demonstrated that minimum ADA can be calculated from the actual output representation and current protocol parameters. The remaining production question is how Accordiax supplies the required ADA resources without forcing the seller to maintain ADA solely for release.

That mechanism is intentionally deferred.

## 10. Beneficiary architecture

The current validator prototype constructs the beneficiary from the seller payment credential.

This is sufficient for prototype validation but is not the final generalized production model.

The production architecture should allow Accordiax to represent the intended beneficiary deterministically while preserving the application's user-to-wallet mapping.

The redesign is intentionally separated from the current prototype so that the validated contract behavior is not destabilized during the current milestone.

## 11. Transaction resource architecture

Cardano execution requires ADA resources for:

- transaction fees;
- minimum ADA requirements for native-asset outputs;
- collateral where applicable.

The production UX should abstract these resources from users who may have no blockchain experience.

The system therefore needs a dedicated resource strategy.

Possible future mechanisms include:

- protocol-level sponsorship;
- service-managed transaction resources;
- fee/resource recovery through the transaction economics;
- dedicated operational wallets;
- other account-abstraction patterns supported by the final Cardano transaction model.

No one mechanism is currently finalized.

The seller is not intended to be the party responsible for manually supplying collateral merely to complete escrow release.

## 12. Settlement lifecycle

### Funding

```text
Agreement accepted
        |
        v
Accordiax creates settlement intent
        |
        v
User authorizes funding transaction
        |
        v
Cardano escrow receives supported asset
        |
        v
Agreement becomes funded
```

### Fulfilment

```text
Funded agreement
        |
        v
Provider performs obligation
        |
        v
Provider submits completion
        |
        v
Customer reviews
```

### Release

```text
Customer approves
        |
        v
Release transaction
        |
        v
Supported asset -> beneficiary
        |
        v
Agreement settled
```

### Dispute

```text
Customer or provider raises dispute
        |
        v
Accordiax records dispute state
        |
        v
Agreement evidence reviewed
        |
        v
On-chain outcome transaction
        |
        +--> release
        |
        +--> refund
        |
        +--> other explicitly supported resolution
```

The exact dispute-to-contract mechanics remain a production contract-design task.

## 13. Analytics and measurement

Dune is not part of the escrow execution itself.

From Milestone 1 onward, the production transaction flow must use the program's standardized transaction metadata label so Cardano activity can be attributed correctly.

The architecture therefore includes an observability boundary:

```text
Accordiax transaction
      |
      +--> Cardano mainnet
      |
      +--> standardized metadata
                |
                v
          Dune / Catalyst Impact
```

The application should not attempt to replace the program's tracking infrastructure with a private dashboard.

## 14. Security boundaries

### Application security

Accordiax is responsible for:

- account security;
- authentication;
- authorization;
- agreement integrity;
- administrative access;
- secrets;
- backend controls.

### On-chain security

The Cardano layer is responsible for:

- validator conditions;
- asset movement;
- datum/redeemer validation;
- authorization enforced by the contract.

### Boundary

The application must never assume that a database state alone proves that an on-chain transfer occurred.

On-chain confirmation should be reconciled into the application state.

## 15. Production dependencies

The production architecture depends on external systems that require separate validation:

- Cardano network;
- Blockfrost or another Cardano provider;
- selected verified stablecoin issuer/policy;
- CIP-0170 tooling and supporting infrastructure;
- wallet infrastructure;
- analytics/tagging requirements;
- regulated conversion/on-ramp providers where fiat entry/exit is required.

A provider being technically available does not automatically constitute a commercial partnership.

Only actual agreements should be described as partnerships.

## 16. Regulatory boundary

Accordiax should not assume that technical decentralization automatically removes applicable financial regulation.

The production architecture therefore separates:

- Accordiax application and escrow technology;
- settlement asset issuance;
- fiat conversion/on-ramp/off-ramp;
- custody or non-custody;
- identity/compliance functions.

The production implementation must use an appropriate regulated arrangement for any component whose legal status requires one.

The specific production issuer and compliance arrangement remain open pending due diligence and real partner agreements.

## 17. Non-goals of the current prototype

The current laboratory does not claim to have completed:

- production stablecoin integration;
- CIP-0170 mainnet integration;
- production wallet abstraction;
- production collateral sponsorship;
- production regulatory framework;
- smart-contract audit;
- mainnet deployment;
- production dispute-contract redesign;
- large-scale external-user adoption.

These are future integration milestones.
